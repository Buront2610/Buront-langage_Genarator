# experimental.2 実装実体の監査

対象: 1.0.0-experimental.2、engine `dd1044404bdf9d10fe548ee0be221df41c2d911e45646db04daeb2d2329e3e84`。

結論: UIだけのモックではない。GiNZA解析、保護値、原文保持、ジョブ・取消・API・再現は実動する。ただし、設計の中心である「状況の関係を操作して新語録を作り、その語り口・魅力・適合を選別する」部分は、固定文型と限定的な検査に留まっている。全タスクが動く製品に近づいたという印象を、テスト数や構造体名だけで与えるのは不適切だった。

設計書1.1・2.2・10.1・11.2・17.2・21.2・29.1とコード、実行結果を照合した。添付設計書は製品の要求資料として扱った。監査のために本体の生成・採用規則は変更していない。

## 優先度付きの指摘

### A1 / P1: 意味操作の実体が話題語と名詞の固定文型挿入に留まる

- 箇所: `packages/core/creation.ts:14`、`:48`、`:78`。
- 主処理は話題トークンを一つ選び、19語の手動概念分類から語を選んで、標準4操作×3文型に差し込む。`realizeOperation`にはFact・主体/対象・条件・原因・対比関係が渡らない。`mapping.source`も元の関係ではなくintent名で、backTranslationは共通の説明文。
- 同じseedで「田中が佐藤を助けた。」「佐藤が田中を助けた。」を比較すると、解析された主体・対象と保持文は正しく変わる一方、創作部分は12/12案で完全一致した。例:「助けることのために勝利を磨きすぎると、勝利を磨くための助けることになる。」
- この一致だけで意味破損とは言わない。しかしコード上も元の関係を写像しておらず、設計10.1・11.2の成立条件・対象領域・述語制約・回収可能性は未実装。原文保持と丁寧形の変更に固定比喩を添える段階である。
- 必要な修正: 複数概念と関係を入力にした操作適用条件、変換前後の関係、許可述語と型、関係を変えた最小正負例を先に定義する。テンプレートの数を増やすだけでは解決しない。

### A2 / P1: 修辞の検証が生成器の許可文字列に依存し、生成器自身の誤りを検出できない

- 箇所: `packages/core/engine.ts:24`、`packages/core/validator.ts:55`、`packages/core/semantic.ts:36`。
- `allowedRhetoric`を生成済みplanの文面から作り、V-rhetoricはそこへの所属を主に検査する。独立再解析はFactClauseだけを対象とし、修辞の実際の効果を検査しない。
- 生成器の回帰不具合を模した内部試験で、保持文「田中が佐藤を助けた。」に「たとえるなら、実際には佐藤が田中を助けた。」を加えた。coreTextと生成器の許可文面も合わせるとV検査9件が全pass、再解析はS-literal、最終候補にも残った。
- これは外部APIから偽planを投入できるという指摘ではない。現行APIはplanを受け取らない。設計21.2が要求する、生成器の意味破損を別の検査で検出する能力が不足しているという指摘。
- 必要な修正: 修辞にも実人物・出来事・極性・完了・帰属の参照を持たせ、抽象主体と現実主体、比喩作用域、未許可の主張を独立に検査する。

### A3 / P1: 追加辞書は編集後の許可判定が更新されず、正常な変更も全案棄却になる

- 箇所: `packages/core/engine.ts:24`、`:44`、`:52`、`packages/core/series.ts:49`。
- 入力「今日は寒い。」は辞書なしで3案。「寒さ=冷え込み」を指定すると通常候補0、要確認候補0、原文fallbackになる。内部12案ともV-planとV-rhetoricでfail。
- 原因は、辞書適用前の許可文字列とsurface.coreTextを使って適用後を照合するため。V-dictionaryにunknownを追加しても、先行failがあるため要確認へは回らない。
- 表示理由も`no_novel_candidate`となり、辞書変更による検査不一致を説明できていない。辞書の単体試験では発見できず、画面に設定欄があっても機能が通っていない具体例。
- 必要な修正: 編集の差分と由来を保持し、修辞の意味検査と新規性を編集後に評価する。安全性を確認できない編集は要確認へ分け、無条件に許可集合へ追加する修正は避ける。

### A4 / P1: 通常の候補選択に実質的な語り口・魅力・文脈適合の判定がない

- 箇所: `packages/core/engine.ts:54`、`packages/core/evaluation.ts:40`。
- S/Q=nullの表示は正直だが、Cは主に原文保持検査の結果、Rは短い文字列の三連続反復検出だけ。文脈に戻れる比喩か、普通の冗談か、説明が破綻していないかは選別しない。
- 監査入力の提示3案は全てS/Q=null、C/R=1。同点処理はIDハッシュ順であり、文体・魅力の順位ではない。学習器導入後もS+Qの単純和で、設計17.2の品質許容帯・軸別比較は未実装。
- 新規性も概念値nullのままcandidate_novelとなる。表記上の未見判定と、設計16.3の概念条件を満たした判定を同一視しない表示・基準が必要。
- 必要な修正: S/Q未学習の段階でも、操作の回収可能性・接続・意味不明の固定負例をC/Rで検査する。人手比較を用意し、未校正の品質をテスト件数で代替しない。

### A5 / P1: 学習用比較データが方式を特徴量で漏らすため、人手ラベルを足すだけでは評価器を完成できない

- 箇所: `scripts/v1/evaluate.ts:23`、`:25`、`:28`、`packages/core/creation.ts:50`、`packages/core/evaluation.ts:28`。
- 新方式だけに37〜66個の特徴を付け、旧方式・普通文・貼付・冗談・誤文にはlength一つしか付けない。
- 保存済み比較データの448側（重複を含む各ペアの左右）を「特徴が二つ以上なら新方式」と判定するだけで448/448側の方式を識別できた。これは好みを当てた精度ではなく、方式識別の漏れを示す数字。
- 品詞・依存特徴は生成候補でなく入力IRから作られるため、同じ原文の12案で完全一致し、同一題材の候補間比較では差分がゼロになる。
- 必要な修正: 全方式の実際の出力文へ同一の特徴抽出器を適用し、方式メタデータを学習特徴から除く。入力由来の構文特徴を候補の語り口特徴として使わない。その後に保留比較・話題置換・外枠除去を行う。

### A6 / P2: 「9系列」の実体は語彙の絞り込みと共通6種類の外枠選択が中心

- 箇所: `packages/core/series.ts:8`、`:29`、`:45`。
- 系列の出典選別は実動する。しかし生成処理は「という話」「だろう」「だべ？」「つまり」「括弧」「なんだが」の固定枠から上位3種を選ぶ。
- night/nega/katuru/ggの上位3枠は同じ。呼びかけ・主張の順番・比較から結論への運びなどを系列別に生成する規則はない。allではこの枠自体を無効にする。
- 外枠を新規性点数から除く処理は実動するが、それだけで系列らしさを外枠除去後にも識別できると証明したことにはならない。現行の全系列テストは候補件数と出典所属を確認している。
- 必要な修正: 用例に基づく系列固有の発話・構成条件と、話題・外枠を除いた比較試験。

### A7 / P2: 出来事の構成ではなく、文単位のラベル付けと並べ替えに留まる

- 箇所: `packages/core/planning.ts:24`、`:48`。
- 設計の例「田中がAを復旧した。Bは停止中で、私は明日確認する。」は3 Factとして解析されるが、構成は2単位のまま。「Bは停止中」と「私は明日確認する」が一つの残件単位へ同居する。
- 原文保持を優先して順序を固定すること自体は正しい。ただし出来事ごとに成果・残件・予定を別節へ割り当てた実装とは言えない。
- 必要な修正: 文境界と出来事境界を分け、接続・条件・帰属を保つ節実現規則を設ける。不確実なら元の文を保持するフォールバックは残す。

### A8 / P2: 一つの不確実な出来事で、他の出来事の明白な時制差まで未検査になる

- 箇所: `packages/core/semantic.ts:17`、`:32`。
- 「田中が確認しなかった。今日は寒い。」→「田中が確認しない。今日は寒い。」で、先頭の過去→非過去の差がある。
- 後半の完了状態unknownによりS-temporal全体がunknownかつrequired=falseとなり、この独立チェッカー単体の総合状態はpassedになる。
- 現在の通常経路では原文一致/限定変換のV検査がこの自由編集を止めるため、そのまま通常APIを突破できるという指摘ではない。再解析検査が弱いことを既存の文字列制限が補っている。
- 必要な修正: 事実・軸ごとに既知の不一致とunknownを分離し、一部分の不確実性で他の明白な不一致を抑止しない。

## 実体があると確認できた部分

- 実GiNZAの解析結果から主体/対象を抽出し、入れ替えに応じてIRが変わる。
- 原値、入力/出力span、有限の丁寧形変換を照合する。自由な事実編集を無条件で通す実装ではない。
- 新規性の名詞抽象化は動く。「白銀の木の塊」など3つの置換例はadaptationに分類された。新規性全体がダミーという結論ではない。
- 系列ごとの参照元所属、ハッシュ、ジョブ処理・API・replayは実装が接続している。
- 既存の152テストは境界・資源・原文保持などの回帰に意味がある。ただしT-13は操作ID・案数・null点数中心、T-15は単発の文字列抽象化中心で、T-14〜18の製品上の品質条件の完了を証明しない。
